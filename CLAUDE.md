Doomscroll is an Expo / React Native app. **iOS is the main platform and Android also matters.** Build and check every feature on iOS first, then make sure it works on Android. Web isn't a target: `react-dom`, `react-native-web` and the `web` config were removed on purpose, so don't add them back. **The app runs on iPhone only** (`ios.supportsTablet: false`), but it must work on every iPhone size, including foldable iPhones.

## Expo changes fast, so don't trust your training data

Expo ships breaking changes with every SDK release. Before writing code that touches an Expo, EAS or React Native API:

1. Read the major version of the `expo` package in `package.json` (currently SDK 58).
2. Fetch the docs for that version: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt and follow its links. Never answer from memory.

The same goes for third-party libraries such as NativeWind, TanStack Query, Zustand and MMKV: check the current docs for setup steps and API names.

## Commands

This project uses **pnpm**. Never use npm, yarn or bun.

```bash
pnpm expo install <pkg>     # ALWAYS use this to add packages; it picks versions that work with the SDK
pnpm expo install --fix     # fix incompatible package versions
pnpm doctor                 # expo install --check + expo-doctor (also runs in CI)
pnpm start                  # start the dev server
pnpm lint                   # ESLint + Prettier, zero warnings allowed
pnpm typecheck              # tsc --noEmit
pnpm format                 # Prettier write
pnpm dlx eas-cli@latest <cmd>  # EAS CLI (use this wherever the docs say `eas`)
```

**Logging**: `console.log`, `info` and `debug` are stripped from production builds (`transform-remove-console` in `babel.config.mjs`), and `console.warn` and `console.error` are kept. Don't rely on `console.log` for anything that matters in production.

**Errors**: `src/app/_layout.tsx` sets `unstable_settings.screenErrorBoundary` (`src/components/screen-error-boundary.tsx`), and nested layouts inherit it. Export a route-level `ErrorBoundary` only when a screen needs a custom fallback.

**Releases**: `eas.json` uses remote app versioning (`cli.appVersionSource: "remote"`) and `autoIncrement` on production. Never set `buildNumber` or `versionCode` in `app.json`. `ios.config.usesNonExemptEncryption` is `false`; revisit it if the app adds custom encryption.

**Before calling a task done**, run `pnpm lint` and `pnpm typecheck`, and both must pass. If you touched config or native dependencies, also confirm the iOS bundle builds: `CI=1 pnpm expo export --platform ios --output-dir <tmp>`.

**Generated types**: `expo-env.d.ts` (which declares `*.css` and other Expo globals) and `.expo/types` (typed routes) are generated by `expo start` and gitignored. On a fresh checkout, or in CI, run `pnpm expo customize tsconfig.json` before `pnpm typecheck`; CI already does. Don't commit those files, and don't work around a missing-type error with your own `declare module`.

**No tests**: don't write test files or add a test framework (Jest, RNTL, Maestro, Detox) unless the user explicitly asks.

**pnpm doesn't hoist packages**: if Metro reports a missing package that a dependency uses internally (for example `react-native-css-interop` from NativeWind), add it as a direct dependency, pinned to the version the parent package expects.

## Code style

- **Tabs, not spaces**: Prettier and `.editorconfig` enforce this. YAML files are the exception and use spaces.
- **Imports**: use ES modules everywhere, including tooling config files. `require()` and `module.exports` are allowed only for static images (`require("./x.png")`). Import from `src/` through the `@/` alias, not long relative paths.
- **Config files** are all `.mjs`: `babel.config.mjs`, `metro.config.mjs`, `tailwind.config.mjs`, `eslint.config.mjs`, `commitlint.config.mjs`. Don't use `.ts` configs: the app tsconfig has no Node types, and NativeWind ships broken types. Use `import.meta.dirname`, not `__dirname`. If a CommonJS package's subpath can't be imported from ESM (for example `nativewind/metro`, which is a directory), import its real file (`nativewind/dist/metro/index.js`) with a comment explaining why, and re-check that path when upgrading the package. Never use `createRequire` or add ESLint exceptions to allow CommonJS.
- **SonarQube-clean**: name every default-exported function (`export default function babelConfig()`, not an anonymous one). Use `String.raw` for strings with backslashes, such as regex patterns, instead of `\\` escapes.
- **Env files**: `.gitignore` ignores `.env*` except `.env.example`. Never commit real secrets, and keep `.env.example` limited to placeholders.
- **TypeScript**: strict mode. Don't use `any`, `@ts-ignore` or non-null `!` unless you explain why in a comment. Prefer `type` over `interface` unless you need declaration merging.
- **React Compiler is on**: don't add `useMemo`, `useCallback` or `React.memo` by hand. Write plain components and let the compiler memoize.
- Components are function components with named props types, always wrapped in `Readonly<>` (`props: Readonly<FeedCardProps>`), which SonarQube rule S6759 requires. Use one component per file, with kebab-case file names (`feed-card.tsx`).
- **Commits** follow Conventional Commits (`feat:`, `fix:`, `chore:` and so on), enforced by commitlint. Husky runs lint-staged on commit and the typecheck on push. Don't bypass them with `--no-verify`.

## Project structure

Code is grouped by feature:

```
src/
  app/                  # Expo Router routes ONLY (screens and _layout.tsx)
  features/<feature>/   # components/, hooks/, api/, store.ts, types.ts
  components/           # shared, feature-agnostic UI
  lib/                  # shared clients and utils (query client, storage, etc.)
  constants/            # theme tokens and app-wide constants
```

- Keep route files thin: they compose components from `features/` and hold no business logic.
- Put business logic in custom hooks inside the feature. Features must not import each other's internals. Move anything shared into `components/` or `lib/`.
- For platform differences, use a `.ios.tsx` / `.android.tsx` file override when the difference is large, and `Platform.select` when it's small.

## Navigation

- Use **Expo Router** for everything. Every file in `src/app/` is a route, and `_layout.tsx` files define the navigators. Typed routes are on, so use typed `href`s.
- Import `Link`, `router`, `Stack`, `Tabs` and `useLocalSearchParams` from `expo-router`.
- Prefer native stacks and native headers. Present modals as routes (`presentation: "modal"`), not as in-screen state.
- Guard authenticated areas with layout-level redirects or protected routes, never with checks inside each screen.
- The deep link scheme is `doomscroll://`.

## State and data

Only add each library when it's first needed, using `pnpm expo install`.

- **Server state** goes in **TanStack Query**. Never store fetched data in Zustand or `useState`. Use query keys that are consistent within each feature, use `useInfiniteQuery` for feeds, and use the query's refetch for pull-to-refresh.
- **Client state** goes in **Zustand**: one small store per feature (`features/<x>/store.ts`). Select single fields with selectors, never the whole store.
- **Persistence**: use **react-native-mmkv** for preferences and cache, wrapped once in `src/lib/storage.ts`. It needs a development build.
- **Secrets** such as tokens and credentials go only in **expo-secure-store**. Never put them in MMKV, AsyncStorage or logs.
- Read environment values from `process.env.EXPO_PUBLIC_*`. Anything with that prefix ends up in the app bundle, so it must never hold a secret. Keep `.env.example` updated whenever you add a variable.

## UI and styling

- **NativeWind v4** (stable, Tailwind CSS v3) is installed. Don't move to v5 until it leaves pre-release. Its setup is spread across `babel.config.mjs` (`jsxImportSource: "nativewind"` plus `nativewind/babel`), `metro.config.mjs` (`withNativeWind`, with input `./src/global.css`), `tailwind.config.mjs` (content `./src/**`), `src/global.css` (imported once in `src/app/_layout.tsx`) and `nativewind-env.d.ts`. `prettier-plugin-tailwindcss` sorts class names.
- Style with **NativeWind** (Tailwind classes). Keep colors, spacing and fonts in the Tailwind theme, not as hard-coded values. Use `StyleSheet` only for dynamic or animated styles NativeWind can't express.
- Support dark mode through NativeWind's `dark:` variants (`userInterfaceStyle` is `automatic`).
- On iOS, prefer native-feeling controls: `@expo/ui`, `expo-symbols` for SF Symbols, and `expo-glass-effect` where it fits.
- Use `expo-image` for all images (`contentFit`, `placeholder`/blurhash, caching), never React Native's `Image`.
- Use **FlashList** for long or infinite lists, which suits a feed app. FlatList is fine for short static ones.
- Use **Reanimated** and **Gesture Handler** for animation and gestures, so animations run on the UI thread. Add `expo-haptics` feedback for meaningful interactions.
- Handle safe areas with `react-native-safe-area-context` (Expo Router already provides the provider). Never hard-code notch or Dynamic Island insets.
- **Layouts adapt to the screen**: size things with flex, percentages and `useWindowDimensions`, never fixed screen widths or heights, so they work on small iPhones, Pro Max and unfolded foldables. Respond to window size changes; don't read dimensions once at startup.
- **Accessibility is required**: give every pressable an `accessibilityRole` and `accessibilityLabel`, make touch targets at least 44×44pt, and respect Dynamic Type (font scaling).

## Native code and EAS

- `ios/` and `android/` are generated (Continuous Native Generation). Never create or edit them by hand. Configure native behavior in `app.json` and config plugins.
- `expo-dev-client` is installed, so we work in **development builds**, not Expo Go. After adding a library with native code, rebuild with `pnpm expo run:ios` or `eas build --profile development`.
- Prefer official Expo modules over third-party libraries, and check the available skills before adding a dependency.
- The build profiles in `eas.json` are `development`, `preview` and `production`. Use `eas build` and `eas submit` for store releases, and `eas update` for JS-only fixes.
- Docs: https://docs.expo.dev/eas/index.md
